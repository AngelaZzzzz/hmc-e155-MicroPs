Lab 6: The Internet of Things and Serial Peripheral Interface

STM32

Building an internet-connected device that toggles an LED and reports room temperature from a DS1722 SPI sensor, served by an ESP8266 web server over UART from the STM32L432KC
Author

Angela Zheng

Published

October 24, 2026

Introduction

The goal of this lab was to build a simple Internet of Things (IoT) device. An ESP8266 WiFi module hosts a web page that lets a user turn an LED on and off and view the current room temperature. The STM32L432KC MCU does the real work:

  • It receives web requests from the ESP8266 over a 125000 baud UART link.
  • It toggles the LED on PA6.
  • It reads the temperature from a DS1722 digital thermometer over SPI, using an SPI driver I wrote with the CMSIS device templates in stm32l432xx.h.
  • It generates the HTML page and sends it back to the ESP8266, which forwards it to the browser.

Beyond the required LED control and temperature display, the web page also lets the user change the sensor’s resolution from 8 to 12 bits. The temperature is displayed with as many decimal places as the selected resolution provides.

Design and Testing Methodology

The GPIO, RCC, FLASH, TIM, and USART libraries and the ESP8266 web server code come from the Lab 6 starter code. I wrote the SPI driver (STM32L432KC_SPI.c/h), the DS1722 driver (DS1722.c/h), and the request handling and web page generation in main.c.

ESP8266–MCU interface

The ESP8266 is connected to USART1 on the MCU, with TX and RX crossed: MCU TX (PA9) goes to ESP RX and MCU RX (PA10) goes to ESP TX. Each time a browser loads the page, the ESP8266 sends the most recent request as /REQ:<tag>\n (for example, /REQ:ledon\n). The main loop:

  1. Reads characters from the UART until it sees \n.
  2. Checks the request for a resolution tag (res8 to res12) and reconfigures the DS1722 if one is present.
  3. Reads the temperature over SPI.
  4. Checks the request for ledon / ledoff and drives PA6.
  5. Sends the full HTML page, from <!DOCTYPE html> to </html>, back over the UART.

When checking for resolution tags, the two-digit tags (res10, res11, res12) are tested before res8/res9, so a request is never matched to the wrong resolution.

SPI driver

initSPI(br, cpol, cpha) configures SPI1 directly through its memory-mapped registers:

  • Pins: SCK on PB3, MISO on PB4 and MOSI on PB5, all set to alternate function 5. The chip enable CE on PB1 is a regular GPIO output, because the DS1722’s chip enable is active high, unlike the active-low NSS of the SPI peripheral.
  • CR1: master mode, software slave management (SSM, SSI), MSB first, and the baud rate, polarity, and phase passed in as arguments.
  • CR2: 8-bit data size (DS = 0b0111) with FRXTH set, so RXNE flags after a single byte.

The DS1722 is initialized with initSPI(0b111, 0, 1):

  • BR = 0b111 divides the 80 MHz clock by 256, giving a 312.5 kHz SCK, well under the DS1722’s 5 MHz maximum.
  • CPOL = 0, CPHA = 1 matches the DS1722 SPI timing, where data changes on the rising edge of SCK and is sampled on the falling edge.

spiSendReceive() waits for TXE, writes one byte to DR, waits for RXNE, and returns the received byte. DR is accessed through an 8-bit pointer so that each write sends exactly one byte rather than packing two.

DS1722 driver

Every DS1722 transaction is two bytes inside one chip-enable window: an address byte followed by a data byte.

Function Address Data Purpose
initDS1722(res) 0x80 (config write) 0xE0 + ((res − 8) << 1) Continuous conversion at the selected resolution
readTempRaw() 0x02 (temp MSB) 0x00 (dummy) Integer part, °C (two’s complement)
0x01 (temp LSB) 0x00 (dummy) Fractional part, in 1/16 °C steps at 12-bit

readTempRaw() combines the two bytes into a signed 16-bit value. The temperature in °C is then raw / 256.

Testing

  1. SPI without the sensor. Before wiring the DS1722, I probed CE, SCK, MOSI and MISO with the logic analyzer. I checked that the configuration write and the temperature reads produced the right addresses, data, clock polarity and phase, and chip-enable framing.
  2. SPI with the sensor. With the DS1722 connected, I decoded the MISO bytes from the scope captures and compared them to the temperature shown on the web page.
  3. Web page. I connected to the ESP8266’s access point, loaded http://192.168.4.1/, and checked that the LED buttons toggled the LED and its status text, and that each resolution button changed the number of decimal places shown.

Schematic

The DS1722 is powered from 3.3 V, with its SERMODE pin tied high to select SPI mode. CE, SCLK, SDI and SDO connect to PB1, PB3, PB5 (MOSI) and PB4 (MISO). The ESP8266 is powered from 3.3 V and connects to PA9/PA10. The LED is driven from PA6 through a current-limiting resistor. The DIP switches between the MCU and the FPGA are open, so the FPGA cannot drive any of these pins.

Results and Discussion

The device works as intended. Loading http://192.168.4.1/ shows the LED controls, the LED status, the current temperature, and the resolution buttons. Clicking Turn the LED on! or Turn the LED off! changes both the LED and its status text. The temperature reads about 23 °C, a reasonable room temperature.

The logic analyzer captures confirm the SPI timing: CE stays high for the whole two-byte transaction, data changes on the rising edge of SCK, and the sensor’s MISO bytes match the temperature on the web page.

The ESP8266 is slow, so a page sometimes takes a few seconds or a couple of reloads to appear. Also, because the page is only regenerated when it is requested, the temperature updates only when the page is refreshed or a button is clicked.

The design meets all of the proficiency requirements. The adjustable-resolution controls go beyond the base specification.

Conclusion

The STM32L432KC parses web requests from the ESP8266 over UART, controls an LED, reads the DS1722 over a CMSIS-based SPI driver, and serves a dynamic HTML page with the LED state and the current temperature at a user-selectable resolution.

I spent a total of hours working on this lab.
